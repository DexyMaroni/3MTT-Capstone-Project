Capstone / Code Walkthrough

Inside FarmLink

How a request becomes a page, why the order tables duplicate data on purpose, and what happens inside the checkout transaction — the parts of this codebase worth being able to explain out loud.

Django 6.1 3 apps / 39 tests SQLite → PostgreSQL

01

What talks to what

Three apps, split by what they own rather than by what they do. This is the split Django rewards: each app owns its models, and the dependencies point one way.

AppOwnsDepends onIn one sentence
accounts User — Who someone is, and which side of the market they're on.
listings Category, Listing accounts What's for sale, and the farmer tools to manage it.
orders Cart, CartItem, Order, OrderItem accounts, listings Turning a selection into a committed purchase.

accounts depends on nothing, so it can't break when the other two change. orders sits at the bottom of the stack and imports from both. If you ever needed to delete a feature, you could remove orders entirely and the marketplace would still browse.

The one that matters

AUTH_USER_MODEL = 'accounts.User' is set in settings.py before the first migration ran. Django bakes the user table into every foreign key in the project. Changing this after migrating means unpicking those references by hand — which is why it's the first decision, not a later one.

02

Following one request all the way down

Take a single click: a buyer opens /listing/3/. Six things happen in order, and being able to narrate them is most of what "understanding Django" means.

The stage most people can't explain

The context processor. Nothing in listing_detail passes the cart count to the template — yet base.html renders a cart badge on every page. That's orders/context_processors.py, registered once in settings.py and run automatically on every single render.

orders/context_processors.py

def cart_summary(request):
    count = 0
    # Short-circuits before touching the DB for farmers and
    # logged-out visitors, so the cost is zero for most requests.
    if request.user.is_authenticated and request.user.is_buyer:
        count = CartItem.objects.filter(
            cart__buyer=request.user
        ).aggregate(total=Sum('quantity'))['total'] or 0
    return {'cart_item_count': count}

The alternative — passing cart_item_count from all fourteen views — works, until you add a fifteenth view and forget.

03

Why the order tables repeat themselves

This is the design decision most worth defending, because at first glance it looks like a mistake. OrderItem stores title, unit_price, unit and farmer — all of which already exist on Listing. A database course would call that denormalisation and mark it down.

Here it's the entire point.

If OrderItem only held a foreign key, every past receipt would silently rewrite itself whenever a farmer adjusted a price. A buyer who paid ₦3,800 would open their order history and see ₦9,999. The accounting would be fiction.

There's a test that pins this down, and it's the one to point at:

orders/tests.py

def test_order_item_snapshots_price_so_later_edits_dont_change_history(self):
    # buy at 3,800
    self.client.post(reverse('orders:add_to_cart', args=[self.listing.pk]),
                     {'quantity': 1})
    self._checkout()

    # farmer raises the price afterwards
    self.listing.price = Decimal('9999.00')
    self.listing.save()

    item = Order.objects.get().items.get()
    self.assertEqual(item.unit_price, Decimal('3800.00'))

The related decision: on_delete

Each foreign key answers "what happens when the thing I point at is deleted?" and the answers here are all different on purpose:

FieldRuleWhy
Listing.farmerCASCADE Delete the farmer, delete their listings. Nothing is left orphaned.
Listing.categoryPROTECT Refuses to delete a category still in use — a guardrail against an admin mistake.
OrderItem.listingSET_NULL Deleting a listing must never erase a sale. The row survives; the link goes null.
Order.buyerPROTECT You cannot delete a customer who has order history.

order_detail.html handles the SET_NULL case explicitly — if item.listing is null it prints the stored title with "(listing removed)" instead of a broken link.

04

Inside the checkout transaction

_place_order() in orders/views.py is the most demanding function in the project, because it's the only place where being half-finished would be a disaster: an order written but stock not decremented, or stock taken for an order that failed.

Why F() and not Python arithmetic

The tempting version is wrong in a way that's easy to miss:

# WRONG — read, then write, with a gap in between
listing.quantity_available -= item.quantity
listing.save()

That reads the value into Python, subtracts, and writes it back. If another checkout commits during the gap, its subtraction is overwritten and stock silently reappears. The version in the code never moves the number out of the database: 

Listing.objects.filter(pk=item.listing_id).update(
    quantity_available=F('quantity_available') - item.quantity
)

That compiles to SET quantity_available = quantity_available - 2. The database does the arithmetic, so there is no gap to lose an update in.

Be honest about this one

select_for_update() does nothing on SQLite. Django's SQLite backend reports has_select_for_update = False and silently drops the FOR UPDATE clause from the generated SQL — verified, not assumed. On SQLite the safety comes from the database-wide write lock plus the atomic block; the row-level locking only becomes real on PostgreSQL.

Saying this yourself is far stronger than being caught by it. The code is written for where it's going, and the F() expression protects you on both.

A detail you might get asked about

Step 2 checks stock against the locked rows, but the total is summed from item.listing.price. Both are read inside the same transaction, so they agree — but the locked rows are the authoritative copy, and computing the total from those too would be marginally tidier. Worth knowing before someone points at it.

05

Three layers of permission

Access control here isn't one mechanism, it's three, each catching a different kind of mistake.

Layer 1 — decorators, for "is this the right kind of user"

@farmer_required and @buyer_required in accounts/decorators.py gate whole views. A buyer hitting the farmer dashboard gets redirected with an explanation rather than a bare 403, because reaching it usually means a stale bookmark, not an attack.

Layer 2 — scoped lookups, for "is this your object"

This is the technique worth showing off. The obvious version:

# fetch first, check after — the check can be forgotten
listing = get_object_or_404(Listing, pk=pk)
if listing.farmer != request.user:
    raise PermissionDenied

versus what the code actually does:

listing = get_object_or_404(Listing, pk=pk, farmer=request.user)

Another farmer's listing isn't found at all — a 404, which also avoids confirming that the listing exists. The permission check can't be skipped by a future edit, because it isn't a separate step: it is the query. That single line appears in both listing_update and listing_delete, and a test proves a second farmer gets a 404.

Layer 3 — the database, for "can this even be represented"

CartItem carries a UniqueConstraint on (cart, listing). Even if a double-clicked button sent two identical requests, the database refuses to store the same listing twice in one cart. The view's get_or_create handles the normal path; the constraint handles the abnormal one.

The one thing I'd change

Both decorators hardcode the login URL: redirect(f"{'/accounts/login/'}?next={request.path}"). The f-string wraps a plain literal and does nothing, and the path is duplicated from settings.LOGIN_URL. Rename that URL and these break silently. It should use settings.LOGIN_URL with reverse().

It works, and it's tested — but if you're asked "what would you refactor?", this is a much better answer than "nothing".

06

The JavaScript is optional, by design

Every interactive feature is a working HTML form first. The JS intercepts the submit and sends it with fetch() instead — and if that fails, hands control back to the browser:

static/js/main.js

.catch(function () {
    // Network failure — fall back to a normal submit so the
    // user still gets somewhere useful.
    form.submit();
});

The server side of the handshake is one header. Views call _wants_json(request), which checks for X-Requested-With: XMLHttpRequest, and return either a JsonResponse or an ordinary redirect from the same function — so there is no duplicated add-to-cart logic.

Turn JavaScript off completely and the entire site still works; it just does full page reloads. The cart quantity field falls back to a visible <noscript> Update button, and the sort dropdown to an Apply button. That's progressive enhancement, and it's worth naming out loud — it's the difference between "I added AJAX" and "I chose an architecture".

07

Where the queries are kept honest

Rendering nine listing cards means touching each listing's farmer and category. Done naively that's 1 query for the listings plus 2 per card — nineteen round trips for one page. The custom queryset fixes it in one place:

listings/models.py

class ListingQuerySet(models.QuerySet):
    def available(self):
        return self.filter(is_active=True, quantity_available__gt=0)

    def with_related(self):
        return self.select_related('farmer', 'category')

    def search(self, term):
        if not term:
            return self
        return self.filter(
            Q(title__icontains=term)
            | Q(description__icontains=term)
            | Q(farmer__location__icontains=term)
        )

Because these are chainable, the marketplace view reads as a sentence — Listing.objects.available().with_related().search(term) — and the definition of "available" lives in exactly one place. When you later decide sold-out produce should still be visible, you change one method, not six views.

The same instinct shows up on the farmer dashboard, where revenue is a single aggregate rather than a Python loop over every sale: 

totals = sales.aggregate(
    units=Sum('quantity'),
    revenue=Sum(F('unit_price') * F('quantity'), …),
)

The multiplication and the sum both happen in SQL. With ten sales the difference is invisible; the reason to write it this way is that it stays flat when there are ten thousand.

08

Questions to have an answer ready for

  • Why extend AbstractUser instead of adding a Profile model?

    Every user here must be a farmer or a buyer — there's no user without a role. A one-to-one profile would create a row for every user anyway and add a join to every query. The role belongs on the user.

  • Why does OrderItem duplicate the listing's data?

    So order history stays true when a farmer edits a price. Section 03 — and there's a test named after exactly this.

  • What happens if two buyers order the last crate simultaneously?

    Both enter _place_order; the transaction serialises them. The second one's stock re-check fails, it returns None, everything rolls back, and that buyer is sent to the cart with an explanation. On PostgreSQL select_for_update() enforces the ordering; on SQLite the database-wide write lock does.

  • How do you stop one farmer editing another's listing?

    The lookup itself is scoped: get_object_or_404(Listing, pk=pk, farmer=request.user). It isn't a check that could be forgotten — it's the query.

  • Why DecimalField for money and not Float?

    Floats can't represent decimal fractions exactly, so money arithmetic drifts. DecimalField stores exact values — the correct choice for currency in any database.

  • What would you do differently?

    Fix the hardcoded login URL in the decorators (Section 05), move to PostgreSQL so the row locking is real, and add a quantity_available >= 0 check constraint so the database itself refuses negative stock.

  • Is it tested?

    39 tests. The behavioural ones live per-app; tests_smoke.py renders every page as the role meant to see it, which is what catches a broken {% url %} tag. Run python manage.py test.
